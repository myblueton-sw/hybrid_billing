# Commands and authority

HYB-340 adds four commands to the existing authenticated command API. All require current user and console AdministerInstallation authorization, active human installation-administrator membership and membership in the existing approvals registry's governor set. Only sample mode is supported. No production policy initialization, financial Approve grant, amount ceiling, charge decision or downstream execution is implied.

| Command | Target | Body | Effect |
| --- | --- | --- | --- |
| financial_policy.current | charge_approval | Empty | Current StageCharge policy, explicitly synthetic |
| financial_policy.propose | Unique proposal ID | policy_revision, approvals, validity_hours, required | Pending policy proposal with immutable proposer and rationale |
| financial_policy.inspect | Service-owned proposal ID | Empty | Historical proposal/decision receipt |
| financial_policy.confirm | Service-owned proposal ID | digest | A different current governor confirms the exact proposal |

Numeric fields use canonical positive decimal integers; approvals is 1–3 and validity_hours is 1–2160. policy_revision must be the next revision at proposal and confirmation. required is a sorted, unique comma-separated subset of attribution, erp_draft, fx, input, mapping, result and rule, including result. These configure prerequisites; they do not supply or certify that evidence. The caller cannot select another stage or impersonate an actor. The existing command envelope supplies rationale, expected revision, request/idempotency IDs, CSRF and actual session. Mutations require existing step-up and refuse under trust hold. Authorized inspect/current reads remain available under hold.

Confirmation rechecks the stored proposer’s current identity, membership, installation authorization and module-governor membership. A fresh-key historical replay cannot bypass those checks. An ordinary same-key command replay follows the command registry's authorized receipt semantics, not a new confirmation. Changed policy fields, actor, digest or rationale cannot rewrite an existing receipt. Superseded proposals do not restore older policies. Competing confirmations of the same next revision cannot both apply.

The bounded service binding stores digest, proposer and immutable reasons beside the existing bounded proposal registry. Unknown demonstration proposals cannot be adopted for service mutations. Supported output capacity is checked before effects: at least16 fields,128 bytes per field, and enough bytes for the configured rationale maximum. Registry changes and service binding assignment occur under the existing server domain lock. This is in-memory synthetic operation, not durable financial storage.

# Impact and historical reads

M01 separately counts pending service-owned financial_policy_proposals by their recorded proposer. Missing/corrupt bindings or an unavailable tally refuse impact preparation rather than reporting zero. Confirmed proposals are excluded. The count does not cancel proposals or represent pending charge requests, pricing policy grants or payments.

B09 uses the request's confirmed historical policy revision. Superseded previously-approved requests retain their single historical approver and decision time; updated time records supersession. This does not establish present approval authority. The reader still refuses unsupported multi-approval/partial/exclusion shapes, and CheckCurrent/Execute continue using current policy and current prerequisites. Current policy replacement therefore does not erase truthful old history or make old history executable.

# Governed amount-authority extension

financial_authority.propose/confirm/inspect/revoke operate on a service-owned proposal ID. Propose requires explicit recipient, currency, canonical exact nonnegative limit, from and to. The derived authority ID is financial-limit-{proposal}; module validation bounds it to128 bytes. Stage is fixed to charge_approval. Both dates are required, validated in2000–2099, and include the complete UTC start/end days. The amount is a maximum absolute amount in the stated currency, without conversion or inferred production defaults.

Propose and confirm require current installation/module governors; proposer and confirmer must differ from each other and the recipient. Recipient must be a currently active human with effective workspace membership. Confirmation rechecks these facts even on a fresh-key historical retry. Inspect and revoke require a current governor. Revoke names the one service-bound module authority and preserves actor, reason and time; it is allowed under hold, unlike propose/confirm. All mutations retain the ordinary session, CSRF, expected-revision, idempotency and step-up envelope.

The immutable bounded binding preserves proposal, confirmation and revocation reasons. All output bounds are checked before effects:23 fields,128 bytes per field and capacity for configured rationale. Pure PrepareAuthority canonicalization creates no records and advances no clock. AuthorityAt returns the module's effective clamped time with its authority snapshot. Receipts derive module_amount_authority from that time and expose authority_as_of, so time rollback cannot falsely reactivate an expired limit. Revocation takes precedence over date status; historical confirmation cannot restore a revoked limit.

M01 financial_authority_proposals counts only pending proposals, separately from financial_policy_proposals and pricing/input permissions. Missing or corrupt service bindings make impact calculation unavailable. The category is Charge approval limit proposals / 청구 승인 한도 제안 / مقترحات حدود اعتماد الرسوم.

The amount-authority extension makes no AddGrant call. Module amount authority alone is not financial approval permission. The separately governed permission extension below supplies direct-human grants; narrowly authenticated decision transport and candidate/prerequisite integration remain required. Existing M03 cannot provision that human-only grant through a console ceiling; that restriction remains unchanged.

# Direct-human permission extension

financial_permission.propose/approve/reject/withdraw/inspect use a service-owned proposal ID. Propose accepts recipient and explicit RFC3339Nano not_before/not_after only. The fixed capability is approve, the resource kind is charge_approval, and the grant covers the complete installation workspace with no field restriction, no client and no console ceiling. Its maximum validity is24 hours; a pending proposal expires after1 hour. The bounded registry holds1000 proposals. No default grant is installed.

Every command, including same-key replay and inspection, requires current authenticated installation and module-governor membership. The closed command family is checked under the existing domain lock before command receipt replay. Unsupported unseeded mode retains the command registry's501 response. Proposal/approval separately recheck the stored proposer and current target; the canonical module-admin set participates in freshness. Proposer and independent approver cannot be the recipient. The recipient must be an active human with effective membership before a new effect. The engine binds actor, rationale and digest before attempting the effect.

Unknown outcomes retain the exact intended grant identity. Before/after-effect faults and lookup failures cannot cause blind recreation. An exact existing revoked or expired grant may resolve uncertainty as historical evidence; it does not restore authority. Replies explicitly mark receipt=historical_decision and recorded_grant_status is historical. Current gate permission, current module amount limits and current candidate prerequisites remain separate checks. Output preflight requires20 fields and1024 bytes per value before mutation.

M01 counts pending, applying and unknown financial_permission_proposals separately as Charge approval permission requests / 청구 승인 권한 요청 / طلبات صلاحية اعتماد الرسوم. Tally failure makes bulk impact unavailable. Hold refuses propose/approve but permits inspect/reject/withdraw; mutations retain step-up. Generic M03 additions refuse the dedicated kind at catalog, request, retained approval and final application. Independently authorized M03 revocation remains available for the actual subject grant. M03 labels the grant in all three languages and explicitly excludes charge-approval eligibility from its console-operation preview.

# Candidate-backed subject preparation

The internal financialSubjectLocked helper now derives an aggregate StageCharge subject from one retained v7 candidate. It verifies raw envelope SHA256, the separately retained input bytes, requested candidate digest/workspace, original CaptureAuthor and complete governed provenance. It rechecks current approved pricing evidence and current input publication/reconciliation, rebuilds the full normalized input from current source/mapping/target/attribution/lifecycle/rows without storing a candidate, and rerates through the existing exact composition boundary. Any input/result mismatch, held/excluded line or unsupported module numeric precision refuses. No rounding to fit the approval profile is permitted.

The current financial policy must match an exact confirmed service-owned proposal and binding; demonstration policy alone is insufficient. Required digests are selected exactly: versioned hb_financial_evidence_v1 input, rule, mapping and attribution hashes; result is the verified full v7 candidate envelope digest. Required fx or erp_draft refuses until actual producers exist. Amount/currency come from the verified result, Author from immutable CaptureAuthor, and Entries is empty. Returned digest maps are defensive. Pure PrepareSubject validates module shape/precision without creating a request or reading its clock.

The hb_financial_target_v1 identity binds workspace/customer/entity/contract/billing profile/provider/account/period/from/to and excludes candidate/request IDs, currency and producer revisions. Replacement candidates within this scope share a target. A different billing profile, provider/account or period is a different target: no cross-scope obligation deduplication is claimed. This internal preparation neither authenticates nor authorizes callers. Future HTTP request/decision transport must authorize the actual session before lookup, recheck all external evidence under the domain lock and only then call the approval module. The separately reviewed transport below now connects these subjects to authenticated requests and human decisions.

# Permission to submit charge approval requests

financial_request_permission.propose_console/propose_human/approve/reject/withdraw/inspect govern a separate ceiling-mode domain. The fixed request capability maps only to gate.RequestApproval on charge_approval, complete workspace scope and no fields. Wire bodies cannot choose capability/action/kind/workspace. Console proposals require explicit not_before/not_after; human proposals additionally require recipient and the exact approved ceiling grant ID. Maximum validity is 24 hours and proposal lifetime 1 hour; registry capacity is 1000. No default grant and no console Approve grant is created.

All six commands require current installation/module financial governors, including before same-key receipt replay. Two independent governors approve; a human recipient cannot propose, approve or reject their own permission. New human effects require active membership and a current matching console ceiling with contained validity. Domain4 maintains independent bindings/ceiling provenance and rejects other domains' ceilings. Final grant construction separately checks boot workspace, fixed capability, console/human shape and static approved ceiling provenance. Uncertain existing effects may reconcile historically after ceiling revocation; absent effects cannot be newly applied under that revoked ceiling.

Receipts carry historical_decision and require 20 output fields/1024-byte value capacity before mutation. Hold permits inspect/reject/withdraw; step-up applies to mutations. Generic M03 additions remain excluded. Independently approved M03 human-grant revocation works, while protected console grants retain their existing restriction. M01 financial_request_permission_proposals counts pending/applying/unknown records separately; tally failure refuses bulk impact preparation. M03/P02 show Request approval plus Charge approval in each language. This permission permits submitting a future charge approval request, not deciding it or bypassing amount limits. No financial request is created by permission provisioning.

# Authenticated charge request and decision transport

financial_charge.request requires current RequestApproval human and console rights on charge_approval. Its target is the financial request ID; wire fields are candidate and digest only. The server rebuilds current governed v7 evidence and derives exact amount/currency, original capture author and economic target under the current owned single-approval policy. It preflights at least 24 output fields, 1024-byte values and bounded provenance capacity before module Request. The immutable binding records candidate/digest, subject, requester, policy, request digest and rationale. Existing module records without a service binding cannot be adopted. Fresh-key reuse requires identical pending provenance and current evidence; terminal requests cannot be revived. Same-economic-scope new requests supersede older pending/approved records through the existing module.

Only financial_charge.approve/reject use the actual-human approval dispatch exception: registered Approval=true, fixed gate.Approve/charge_approval, and only the server-supplied ConsoleClient is removed. The actual session is admitted before a bounded internal original-author lookup. Missing, foreign, corrupt or unauthorized bindings disclose no record metadata. CheckApproval/RecheckApproval preserve original-author exclusion; requester exclusion is checked separately before replay. Fresh decisions rebuild current producers and require the exact retained subject/current policy. Approve requires current module amount/currency/date coverage. Reject requires current decision permission and separation, but not amount coverage; reason is one of incorrect_amount, missing_evidence, policy_violation or other, with separate human rationale. Trust hold refuses requests/approval but permits rejection and historical review; all mutations require step-up. Same-key receipts require current permission and describe historical decisions, not current eligibility.

financial_charge.review independently requires approval_review/View/approval_evidence and its console intersection. Submission or decision permission alone does not grant this read. The bounded historical_evidence result includes recorded amount/currency, author/requester, candidate/digest, policy and evidence digests, with current_eligibility=unchecked and amount_basis=rated_candidate_total. Mutation receipts omit amount and raw source data. No raw supplier Cost or source rows are exposed. The calculated candidate total is not asserted to be tax-inclusive gross, a final invoice or a payment. New financial requests are not appended to the legacy demonstration index. The B09 projection extension below derives their rows directly with a truthful amount basis.

M01 financial_charge_requests separately counts pending actual requests by requester and fails closed if tally evidence is unavailable. It reports rechecked=false with explicit copy that the requester's submission permission is not rechecked at decision time. Requester suspension does not automatically cancel an existing request. This does not bypass the decision actor's current permission, original-author/requester separation, current producers, policy or approve amount limits. Defensive binding reads prevent callers from mutating retained evidence. Existing W-23 downstream and screen integration work remains active.

# B09 historical projection extension

GET /api/approval-review now derives a bounded union of legacy index entries and service-owned financialCharges, with a combined maximum of 1000. Workspace filtering, cross-source duplicate refusal, exact binding validation, historical single-approval PolicyAt and deterministic ID ordering precede filtering/paging. No second retained financial index is created. Snapshot hashing includes the projected new facts and changes after actual requests/decisions.

Legacy sample rows retain gross basis and producer_unbound. Service-backed StageCharge records use rated_candidate_total and recorded Pending is pending. Their current_checks_unverified explanation explicitly says this historical read did not recheck current prerequisites or permission; the screen displays it separately from failed-validation blockers. Current authority/eligibility, deadline and ERP applicability remain unknown. Exact amount strings and original author are preserved; requester and positive policy_revision are added as a pair. The client accepts the old exact record shape or the new complete pair, rejecting null/partial pairs, unknown keys and unknown bases. Older records display missing provenance as not provided, never copied or inferred.

B09 details show requester after author and recorded policy revision after timestamps. Mixed synthetic-environment notices and row tags no longer call actual synthetic requests fake examples. The screen remains read-only: commands=unconnected refers to its action binding, not absence of the separately implemented HTTP commands. Neither historical approval nor a snapshot is execution authority. Authenticated decision preparation is now described below; screen actions remain the next integration.

# Current module decision preflight

Registry.CheckDecision evaluates fresh decision conditions without recording a decision. It refuses historical deciders, including a still-pending multi-approver request, and shares current human/state/separation/coverage/exclusion validation with Decide. Decide retains its existing historical replay behavior. Rejection does not require amount coverage. The check may advance the monotonic clock watermark but changes no request or decision collections. It is not authenticated authorization, a reservation or permission to execute; a later mutation repeats current checks. B09 controls remain outstanding. # Authenticated current decision preparation

financial_charge.prepare is a non-mutating command with the separate B09 read permission and console intersection, checked before service-binding lookup. A matching selected request digest is required. A fixed bounded current_decision_preparation response preserves exact rated amount/currency, author/requester, policy, state and digest, and returns the current global revision, a post-check wall-clock checked_at and separate closed approve/reject outcomes. The command does not create a financial revision, reservation or decision.

Actual human decision permission and original-author/requester exclusion precede current producer probes. Authorized actors require pending state, unchanged owned candidate/policy evidence and no stranded effects. Approval is unavailable during hold; rejection remains available if other checks pass. Each action uses its actual mutation-name step-up check and module fresh-decision check; only approval needs amount/currency/stage/date coverage. Missing MFA support is prerequisite_failed, expired authentication requires reauthentication, and an invalid session remains an authentication refusal. Required future user rejection reason/rationale are still validated on mutation. Permission failure, stale evidence, unavailable dependencies, insufficient amount authority and nonpending states remain distinct. Unknown internal outcomes fail closed.

Later commands repeat all current conditions and revision checks. A successful preparation is not a future authorization or historical decision receipt. Existing audit/rate state, role expiry sweeps and monotonic module clock bookkeeping are unaffected. B09 action binding remains outstanding. See [plan](decision-preparation-plan.md) and [verification](decision-preparation-verification.md).
