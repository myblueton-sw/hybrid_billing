# Model and identity

Use a versioned typed graph rather than company/provider/account as one universal tree. Internal company/tenant authority remains separate and existing FOCUS provider/account/subaccount assignment is the access gate. A shared payer or organization never grants access or reveals sibling nodes/counts. Canonical native identity is installation namespace plus provider, cloud/partition/realm, native kind, kind-specific namespace and original native ID. Collector/source connection, labels and current parent are provenance, not identity. Preserve native ID lexical form and aliases without asserting alias equivalence; reject ambiguous identities/duplicate aliases in a namespace. Scope AWS OU/root IDs by organization; scope account-local Alibaba entities by account; scope VMware MoRefs by service-instance UUID. Azure ARM path changes produce new observed identity/history, not an invented stable identity.

A pinned provider profile registry specifies native kinds/common categories and allowed directed child-to-parent relation pairs. Keep organization membership/management role, resource containment, billing linkage/transfer/subscription mapping, identity association and VMware placement/attachment distinct. Validate per-relation cardinality/cycles only where applicable; do not impose one parent across all axes. Every edge and fact-to-native binding has explicit valid-from/valid-to and source observation time/evidence class/reference. A binding must cover the whole source charge interval; ambiguous/partial validity remains explicitly unresolved. Bound nodes/edges/depth and input bytes.

FOCUS BillingAccountId and SubAccountId always normalize into observed invoice-scope/usage-scope references. They do not automatically become a CSP management account, Entra tenant, GCP organization or VMware vCenter. Extra native metadata enters only through a trusted operator-provisioned manifest using exact existing provider/account/subaccount/tenant assignments. Unknown providers/native types, namespace errors, dangling/cross-provider references and overlapping ambiguous bindings reject. A native manifest cannot add accounts or tenants to authority. Account-type distinctions preserve invoice scope (e.g. Azure FOCUS billing profile) separately from the native top-level billing account.

## Design review resolutions

DBA and architecture/security design review accept the model with explicit grouping constraints: every traversed edge used for ancestor attribution must cover the entire charge interval. Partial/unknown validity is unresolved, never replaced by observed_at/latest parent. A kind/axis grouping accepts exactly one matching ancestor per fact; multiple candidates reject additive grouping, including multi-network/datastore attachments. Missing candidates use an explicit unresolved bucket. No allocation weights are invented. All query/paging paths pin the selected enrichment digest; legacy single-batch paging requires that digest as well. Full native inventories remain source-supplied assertions, not proof of historical valid time.

Native role bindings are a nonempty subset of observed billing/usage/resource/identity roles. Missing native billing/identity remains unknown, with the separate observed FOCUS scope preserved. A VMware vCenter/service instance must never be invented as a payer/invoice scope merely to fill a required native billing role. Typed-native status means observed native bindings, not complete source hierarchy or all roles.
