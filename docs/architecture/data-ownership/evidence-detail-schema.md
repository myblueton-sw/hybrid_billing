# Evidence and detail schema

Part of [HB-21 logical schema](logical-data-schema.md). All entity names and fields are proposed logical vocabulary. Transactional metadata owns eligibility and financial decisions; protected immutable detail owns permitted evidence and explanation; read projections/indexes are derived. Object storage/Parquet is the recorded foundation; exact table/catalog/engine and physical files remain unselected. The >100M source records/day premise does not set a maximum or certify throughput.

## Source receipt and eligibility metadata

| Entity / grain | Required fields / relationships | Identity and failure constraints |
| --- | --- | --- |
| `SourceProfileRevision` / approved source contract | Scope, provider/authority/account, collection family, available resolution, identity tuple/multiplicity/revision rules, snapshot/append/hybrid mode, coverage criteria, cross-transport precedence, field/unit/basis schema, fetch/credential audience and capability evidence | Preserve all eight collection families and conditional/later profiles; no complete-snapshot assumption from transport. Unsupported basis/resolution is explicit, not fabricated detail. Missing profile blocks eligibility. |
| `Connection`, `SourceAccount`, `SourceAccountAssignment` / source and attribution | Scope and canonical IDs, external namespace/account, profile revision, secret reference, expected connection revision, approved attribution history | Connection success is not source completeness or billing verification. Provider payer/account does not establish customer or legal responsibility. |
| `SourceReceipt` / one transport attempt | Receipt ID, scope/account/profile, method, received time, producer request/page/file references, bytes/counts/digests, completeness/quarantine state, registered protected artifact refs | Receipt ID distinct from source economic identity. Same source through API/upload deduplicates by economic semantics, not transport ID. Partial or hostile evidence cannot replace complete scope. |
| `SourceEconomicIdentity`, `SourceRevision` / stable economic occurrence and correction | Canonical tuple, collision-checkable original identity, multiplicity, scope/period, revision/predecessor/correction links, payload digest and authority evidence | Exact complete-scope uniqueness or durable incremental identity state. No hash-only or probabilistic deduplication. Ambiguous correction/duplicate blocks; expired replay identities make out-of-horizon arrivals ineligible. |
| `SourceArtifact` / immutable permitted object version | Scope, artifact ID/version, protected locator, digest/bytes, schema/key refs, retention-origin time, ownership/disclosure and shared-dependency refs | Verify completed bytes before exposure. Shared payer originals are protected; no general customer raw URLs. Encrypted/readability/key dependencies retained. |
| `CoverageEvidence`, `ComparisonEvidence` / candidate scope and method | Expected versus observed pages/files/records/periods, independent comparison source/method/revision, compatible counts/totals, exclusions and blocker findings | Unknown coverage never zero. Comparison must be independent and complete for required basis; no self-comparison proof. Coarse evidence cannot certify finer detail. |
| `InputCandidate`, `InputDecision` / one immutable proposed release and confirmation | Scope, candidate/current scope revision, manifest digest, mapping/attribution/profile revisions, validation/comparison evidence, actor/authority, decision time/rationale | Explicit `input.confirm_publish` binds server digest and current authority. Reject only unpublished candidate; race with publication conflicts. Eligible history not rewritten to rejected. |

## Fixed release and object/table references

| Entity / grain | Required fields | Constraint |
| --- | --- | --- |
| `BusinessReleaseManifest` / complete immutable release | Scope, release ID/type (`input/result`), scope predecessor revision, candidate/run, schema/policy/mapping/attribution refs, full partition inventory, compatible total inventory, evidence digest, publication decision, completeness and recorded time | Multi-table/snapshot set fixed as one business release; read exact refs, never unqualified latest catalog head. Result publish requires full verification; financial approval remains separate. |
| `ReleasePartition` / release member | Release ID, partition ID, dataset role/grain, schema revision, immutable snapshot/object refs, digest/bytes/row counts, coverage/exclusions and typed quantity/money totals | All declared partitions verified. Distinguish unknown/partial/empty. Totals grouped by unit, currency, semantic measure and basis, never one scalar across currencies. |
| `TableSnapshotRef` / optional managed-table snapshot | Scope, dataset/table identity, catalog namespace/revision, immutable snapshot ID/digest, schema/evolution version, metadata/data/delete-file refs | Applicable only if managed-table design adopted. Parquet file format is not a transaction/catalog service; catalog commits do not approve inputs/amounts. |
| `DatasetCommitOperation` / external catalog/object publication | Logical mutation domain, expected snapshot/owner revision, operation ID/digest, generation/fence, prepared refs, attempted/confirmed/unknown state and reconciliation evidence | Unknown commit prohibits blind append or orphan deletion. One conditional publication coordinator per mutation domain; lease expiry does not prove writer stopped. |
| `ArtifactDependency`, `RetentionPin` / protected usage edge | Owner purpose/record/release/job to exact snapshot/artifact/schema/key/policy dependency; scope, retention basis, expected lifecycle revision and pin state | Reserve dependencies before publication/read/export under lifecycle serialization. Issued-history pins follow approved retention, not indefinite retention. Expiring technical lease alone cannot unpin unresolved commit/history. |

The proposed publication sequence is: prepare immutable bytes/snapshots → verify schema/identity/coverage/counts/totals → reserve lifecycle references → explicit confirmation with current authority and expected predecessor → publish decision/release/eligible pointer/dependencies/outbox in authoritative metadata. A catalog commit, object upload and metadata transaction are not a distributed atomic write. Prepared candidates stay noneligible until reconciliation; cleanup consults pending and unknown operations as well as reachable published manifests.

## Bulk fact grains and column groups

Common bulk columns: Scope, canonical fact ID, source economic ID/revision, exact dataset/release/schema revision, business/recorded time, applicable attribution and policy revisions, retention origin and permitted quality/basis. Composite keys cannot be reset by file partition, compaction or ingest run. Logical schema types follow [common types](logical-data-schema.md#common-types-and-reference-rules); Parquet physical representations are not selected here.

| Dataset / one row means | Required domain columns | Version and aggregation rules |
| --- | --- | --- |
| `RawEvidenceRecord` / one permitted source record occurrence | Source artifact/version and exact record locator; native economic key/multiplicity, source revision/correction; declared native dimensions and unit/money values where supplied | Exact source bytes remain protected artifact. No prompt/response/card payload capture by default. Coarse source records cannot manufacture hourly/resource detail. |
| `NormalizedUsageFact` / one declared measurement grain | Account/customer/contract/org attribution refs; service/resource/time interval and resolution; quantity/unit/conversion revision; event/counter/gauge/interval semantics, reset/rollover and quality (`actual/estimated/unknown`), original lineage | Counter snapshots and component events not added together. Gauge aggregation needs approved operator/time basis; missing intervals remain unknown. Mapping/correction is new revision, not overwrite. |
| `CostComponentFact` / one cost basis component | Provider/internal cost component, quantity if applicable, Money including basis, cost period, responsibility, provider commitment/Marketplace flags and eligibility, FX lineage | Billed/effective/list/contracted bases are separate alternatives, not additive measures. Consume provider RI/SP/CUD results; no new CSP amortization/optimizer engine. Direct purchase cost is not automatically MSP selling charge. |
| `InternalCostFact` / one approved internal cost component/period | Asset/resource and cost-policy refs, depreciation/power/space/license component, approved cost/time basis, idle/shared classification and source evidence | Internal depreciation separate from CSP commitment results. No invented depreciation rates. Complete shared-cost pools preserve unallocated/idle and residual explanations. |
| `MarketplaceComponentFact` / one role-specific economic component | Buyer/seller/infrastructure responsibility, purchase/fee/net-settlement component, authority/currency/basis, commitment-eligibility evidence and related-component refs | Buyer cost, infrastructure cost, seller fee and net settlement cannot be blindly summed. Settlement evidence is not customer receipt or pricing approval. |
| `CalculatedComponentFact` / one reproducible monetary component | Run/result, customer/contract/org revisions, component (`base/discount/fee/min_max/FX/tax/rounding/credit/adjustment/allocation`), Quantity as applicable, Money, formula/numeric/engine versions, pool/operand refs, stage and correction links | Preserve quantity → base → discount → fees → min/max → FX → tax/rounding default order and approved exceptions. Fixed fees explain contract basis rather than invented usage. Signed semantics field-specific. |
| `AllocationShareFact` / one pool/member output | Pool/revision/digest, canonical target ID, exact weight, full denominator, unrounded share when applicable, final signed quantum result, remainder/tie rank and policy/algorithm | Full-pool conservation checked before result publication. Zero weight allowed when total positive; tie order uses immutable ID. Currency/basis/target totals must match pool. |
| `ContributionEdge` / one typed fact-to-component contribution | Unique edge ID and endpoint dataset/revision/fact refs; role (`source/quantity/amount/allocation_basis`), contributed quantity/money/weight where meaningful, pool/calculation refs | Many-to-many sparse graph; heterogeneous edge roles never added indiscriminately. Exact declared input/result lineage and no duplicated edge semantics; source original cost not repeated by allocation fan-out. |
| `ReadProjectionFact` / one fixed permitted derived grain | Source release set, dimension/schema revision, exact semantic measure/basis/currency, completeness/as-of and optional source lineage | Dedup/version and compatible exact sum guards before financial use; projection never grants approval/Claim. Current row/field access before aggregation/output. |

Provider-native extensions use versioned typed namespaces with explicit applicability and disclosure. Frequently queried dimensions need approved field contracts; an arbitrary map does not promise efficient field lookup. Dynamic fields, metadata/statistics, object locators and error messages are protected by the same query authority. Schema evolution specifies compatible read/write versions, unit/meaning changes, backfill and historical reproduction before physical adoption; incompatible semantics receive new schema/version, not silent casts.

Detail-to-document lookup is `document line → permitted contribution/component refs → exact result/input release → source record/artifact`. Keep sparse lineage datasets and bounded locators rather than storing every raw row or expanded join in the transactional financial command. When full-pool operands contain hidden customers, disclose an approved safe explanation without changing the economic denominator.

## Lifecycle and coherent recovery metadata

| Entity / owner | Required data | Integrity rule |
| --- | --- | --- |
| `RetentionPolicyRevision`, `LegalHold` / lifecycle | Class/scope, retention-origin basis, duration/window/grace, approved purpose/owner, protected target and hold revision | Actual durations unresolved. Copy/compaction/replay does not reset age; legal hold independent of operational billing/delivery/collections hold. |
| `ArtifactLifecycle`, `ArchiveTransfer`, `RecallJob` / lifecycle | Exact artifact version, active/archive/recall status, target digest/readability/decryption/counts/totals/dependencies and verified reference switch | Interrupted/corrupt transfer retains valid source or honest unavailable state. Recall cannot issue a document or create new Claims. |
| `DeletionDecision`, `StoreDeletionEvidence`, `Tombstone` / lifecycle | Exact target/dependency set, approved policy/hold checks, monotonic decision sequence, active/projection/object-version/backup progress and as-of | Immediate logical denial distinct from physical removal. Mixed-customer files need verified retained-row rewrite where permitted; old snapshots/versions/backups prevent a false deletion claim. |
| `ControlWatermark`, `WithdrawalDecision` / independent control | Authority stream ID, monotonic committed sequence/epoch, confirmed completeness/freshness, eligible/denied targets and integrity evidence | Separate revocation/deletion/trained-artifact withdrawal streams; one local timestamp cannot prove latest controls. Gap/stale/unavailable stream blocks affected serving/resume. Exact freshness bounds OPEN. |
| `RecoveryManifest`, `WriterGeneration` / operations + domain owners | Coherent transactional backup, catalog/snapshot/object/delete-file/schema/key/policy refs, verified control watermarks, quarantined unknown commits/effects and fence generation | Fence old writers/credentials, verify dependencies and latest independent controls, reconcile unknown catalog/financial dispatch before resume. Restore does not reopen consumed Claims or prior grants. |

GC/compaction/snapshot expiration serializes against new business dependencies, holds, active-reader pins and uncertain commits. Generic object-age TTL cannot delete managed evidence. Projection rebuild only reads still-permitted retained eligible releases and preserves current controls. Audit stores bounded decision/evidence references and required actor/time/purpose, separate from sampled telemetry and bulk payloads.

## Access patterns and physical design worksheet

| Read/write class | Logical routing and keys to measure | Required physical evidence later |
| --- | --- | --- |
| Current customer/workflow/Claim | Scope + canonical identity/status/revision; exact obligation overlap domain | Bounded indexes, exclusion/serialization design, lock/retry/transaction size and growth |
| Sustained intake and corrections | Account + source economic scope/revision; complete release identity validation | Actual source multiplicity, expansion, row widths, burst envelope and exact dedup cost |
| Monthly close and allocation | Fixed period/contract/policy/release and complete pools | Scan/shuffle/spill, skew, allowance pool sizes, component/bridge fan-out, close/catch-up deadlines |
| Dashboards/history/drill-down | Scope/time/service/resource; pinned release and bounded source locators | Lake/serving route comparison; predicate pruning and selective lookup verified with chosen writer/readers |
| Export/AI retrieval | Authorized fixed target/release and current recipient/field controls | Concurrency/bytes/time budgets, current-authority checkpoints and complete output reconciliation |
| Archive/GC/recovery | Policy/class/retention origin plus full dependency and control graph | File/snapshot rewrite amplification, request counts, metadata growth, N-1/storage pressure and restore continuity |

Measure source rows, normalized facts, monetary components, bridge edges, obligations/atoms/intervals, revisions, snapshots and serving copies independently. At 100M/day a 30-day reference is 3B source rows before expansion; the owner premise is greater, not a sizing cap. Row width/peak/retention and processing amplification remain unknown. Do not choose one physical partition per tenant/customer or one SQL row per source Claim without cardinality evidence.

Remaining design gates: actual per-source field/key/multiplicity profiles; unit/FOCUS/basis mappings; representation of numeric coefficients/scales; physical file/table grain, sort/partition/index and schema evolution; selected catalog/engine delete/commit/pin/fence support; safe maximum financial atomic boundary; resource budgets and operational owners. Runtime, DB constraints, file-format compatibility, security enforcement and scale scenarios are **NOT_RUN / UNVERIFIED**.
