# Session lifetime and render purity

Add a dedicated recovery context provider inside authenticated ServiceContext in Service.tsx, wrapping the existing service children without DOM changes. The provider stays mounted across locale/view navigation and owns exactly one active user/workspace/session-CSRF/client scope. Capture these values in memory only; never persist or log the scope or pickup references. The visible provider value must match the current client and canonical session synchronously, before passive cleanup, so a new scope never receives the old store. Use the authenticated Service owner's authoritative session predicate, reading sessionRef, which setSession already updates synchronously before scheduling React state. Pass that stable predicate explicitly; do not invent authority from a provider-local copy. A provider layout-owned token binds the committed client and copied session fields. Layout cleanup invalidates that token and disposes the old store on client/scope replacement or authenticated unmount, before passive cleanup. The layout token makes client changes effective at commit without mutating refs or registering listeners during render. Every read, submission, collection, mark, observation and asynchronous completion checks both this token and the authoritative current-session predicate, not just the context value. Thus a captured old store is also fenced.

Construct and activate the store only in the committed provider effect. Construction has no global event registration. Effect setup captures the matching live layout token, creates the store and attaches actual authentication-loss, deliberate-leave and unload handling. Both layout and passive cleanup dispose idempotently; all subscriptions, entries and marks are released and pending callbacks fenced. Gate recovery consumers until the matching effect-created live store is published. Store construction receives the token/current-session predicate and never bypasses it. React development StrictMode setup/cleanup/setup creates a new live store rather than reusing a disposed instance. An immediate authentication-loss callback prevents publishing that store. Same-scope M04 component unmount does not dispose the provider. Authentication loss or authenticated provider unmount does.

Expose a disposed state and idempotent disposal. Disposed stores refuse new submission/collection and ignore marks, listeners and late outcomes. Existing submit outcomes already compare entry identity; disposal must invalidate those identities before an outstanding promise settles. Keep reference-bearing entries in memory only. No resolved secret payload belongs in store state.

# Exact observation and recovery truth

Replace population reconciliation with known-credential observations bound to the captured service ID, credential ID, current scope and read-start sequence. A read started before issuance, mismatched IDs, failed lookup, page absence or unavailable state proves no terminal outcome. Retain issued references for those cases.

Only authoritative current revoked/expired or returned-once evidence can resolve a post-issuance matching entry. A never_collected/not-open observation is nonterminal because original issuer authority can be temporarily unavailable; keep its reference. Returned once is not safely stored. Preserve an unstored reminder when actual collection succeeds or terminal read-back establishes an unresolved return, until the user confirms storage or revocation. Unknown issuance replay still sends the original attempt, revision, days and rationale. Exec receives copied immutable stored days/rationale explicitly; the actual Live caller must send those arguments rather than a mutable caller closure. Unstored markers carry canonical service and credential together; neither page membership nor the current selection is a fallback. Reconciliation acts only on the matching retained issued entry, so later returned-once reads do not recreate a marker after successful storage acknowledgement. No new issuance or pickup right is inferred from metadata.

# One-time collection ownership

Opening Reveal does not consume its local recovery entry. The provider-owned store permits collection only for its exact retained credential/ref and original AdminClient. Maintain a pending-only single-flight promise keyed by that exact reference. StrictMode effect replay and same-scope observers attach to the same pending GET; they never automatically send a second consume. Remove the pending promise from store ownership before settling its consumers, and never retain a resolved promise/secret. Check document visibility both before creating collection intent and immediately before transport. An unsent hidden request retains its reference without becoming an unknown delivery; later visible collection requires deliberate action. Explicit release cancels matching pending/unknown operations before clearing entries, so late successes cannot recreate reminders.

A matching successful response in the still-active scope retires the issued reference and records an unstored credential marker. A disposed/changed scope drops the result without publishing it. A network failure leaves the reference and unknown collection outcome; a later attempt requires an explicit user retry, not effect replay/remount. A response for a different credential or malformed result fails closed without presenting or retaining its secret; preserve unknown/no-auto-retry state until an explicit retry or authoritative canonical observation. Actual canonical read-back may establish terminal return/revocation/expiry separately.

Reveal keeps only its currently displayed secret in component memory. Its effect subscribes to one pending operation with a local active observer; cleanup suppresses that observer and clears displayed content, without invalidating another live observer of the same operation. The pending request itself is not aborted into an implicit retry. Pagehide/authentication loss clears displayed content and invalidates that Reveal observer generation, so a pending response cannot repopulate a hidden or BFCache-restored document. A subsequent visible observer requires a deliberate user action, not automatic recollection. Storage confirmation and explicit revocation retain their existing deliberate actions. No clipboard/log/persistence integration is introduced.
