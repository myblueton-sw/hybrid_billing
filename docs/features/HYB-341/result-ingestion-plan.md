# Independent packet and retained history

Propose accepts original UTF-8 JSON bytes, at most 4096 bytes, through the existing strict exact-case/duplicate/unknown/null/lossy-Unicode rejection machinery. Required fields: Mode=synthetic, Profile=synthetic_result_one_to_one_v1, Evidence (source reference), Preparation, PreparationDigest, Connection, External, Revision (integer in 1..2147483647, checked before module int use), Currency, Customer, Period, Rows. Each row supplies ID, Line (preparation line identity), Product (external mapped product), Unit, Net, Tax and Quantity. IDs are canonical bounded identifiers; numbers are canonical nonnegative decimals, quantity positive, within the retained connection scale and existing candidate numeric profile. Limit rows to 100 and canonical packet/snapshot sizes before retention. Never derive reported amounts or reported products from preparation. Hash original bytes and canonical parsed content separately; bind both hashes, actual proposer, reason and owned historical preparation into the proposal digest. Preserve original bytes and return defensive parsed copies.

Require a successfully recorded service-owned preparation receipt and exact preparation/connection/currency/customer/period attribution. Resolve its immutable document basis from owned records, even if that evidence or financial approval later became stale/revoked. Propose and confirm retain well-formed reported discrepancies: wrong product/unit, line coverage or net/tax/quantity become explicit comparison outcomes, not a fabricated match. Missing/malformed or foreign identity refuses. A matched comparison is only against the retained preparation, not current eligibility, external ERP confirmation or final amount approval.

Later-revision proposals remain immutable history. The first profile does not rewrite an already owned external document: Document retains stale links and Link cannot freely replace existing allocations. Application of a replacement revision therefore explicitly refuses until a reviewed replacement protocol exists. Exactly one result proposal digest may be confirmed per workspace/connection/external/revision; conflicting same-revision confirmation refuses. Derive the monotonic highest-confirmed revision/digest from immutable confirmation events, including subsequently revoked records. An older proposal may be confirmed as historical-only without displacing that watermark. Only the exact watermark digest may be freshly applied or recovered; revocation cannot lower it or silently restore an older report. A newer confirmation or revoked authority can therefore strand a partially applied older operation: ownership stays unresolved and is never released or treated as absent. Completed receipts remain historical even when fresh apply/recovery later refuses. The full ticket retains replacement support as a subsequent obligation rather than claiming it implemented.

# Dedicated governance and current checks

Every method checks the actual current human session, matching workspace/user, dedicated result namespace and human/console intersection before lookup. No delegation or preparation/document/financial right substitution. Propose requires ProposeERPResult; it is blocked under hold but does not require current financial eligibility to retain historical discrepancy evidence. Confirm requires a different ConfirmERPResult actor, current original-proposer subject authority, exact immutable digest and no hold. It attests supplied evidence, not a successful financial reconciliation. Revoke uses RevokeERPResult and remains available under hold or stale producers; it never deletes applied ledger history or unresolved application ownership. Inspect requires dedicated ViewCost and labels historical comparison/current eligibility separately.

Apply requires ApplyERPResult, confirmed nonrevoked evidence, exact matched comparison, current owned charge approval, current confirmed document and unchanged current connection/mapping/survey facts. Require current original proposer and confirmer result authority at use. Hold blocks application. The applying actor need not be the original preparation actor, but the preparation actor and immutable receipt remain bound; the actual applying actor owns all Link calls and retries. Recheck these prerequisites before historical receipts or recovery. Later denial does not establish that an earlier effect did not occur.

# Ownership-first multi-step application

Before any ledger write, reserve a bounded immutable application record binding workspace/result digest/preparation receipt, connection/external/revision, complete intended document/links and actual applying actor. Also reserve the external document identity and preparation identity so another result/key cannot duplicate or replace the operation. Preflight all bounded retention, reservation and eventual receipt representation before the first invocation. Distinguish not-found from unavailable/error on DocumentOf; only not-found can permit initial creation. Refuse adoption of any pre-existing unowned document, even identical. Refuse unexpected existing linked documents or allocations. Under the caller-held service domain lock, call the same actual ledger's Document, then each Link. These are not atomic as a group.

After invoking any possibly mutating operation, an error or interrupted receipt is unknown. Keep ownership and intent. Recovery rechecks current rights/evidence, preserves original actor/packet/key and inspects existing DocumentOf plus the coherent ResultOf. Resume only absent intended links. An existing document must match the exact owned revision/rows/author; every existing link must be an intended same-actor exact allocation without stale/foreign/extra links. A completed receipt is created only after coherent ResultOf proves the exact owned submission, complete one-to-one row/product set, exact links, no unexpected documents/stale allocations, matched per-line amounts and complete document total attribution. Historical receipt storage never changes the module's prepared status or creates Observe/Submit/Post commands.
