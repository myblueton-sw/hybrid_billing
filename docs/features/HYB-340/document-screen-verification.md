# Implemented scope

[HYB-340](https://linear.app/myblueton/issue/HYB-340), machine:mac_mini. Root implemented the [reviewed B09 document design](document-screen-plan.md) using the [strict client foundation](document-client-verification.md) and [session controller](document-controller-verification.md). The new section belongs to selected service-owned financial requests, including historical requests. One scope-owned hook supplies both responsive detail copies. Hidden copies do not fetch or own separate submission locks. Request/session changes invalidate advisory data while retaining session-owned operation evidence.

The section separates document history, preparation history, retained basis/events, current permission and packet readiness. Structured fields require explicit ERP selection, unit, evidence, quantity, tax, declared totals and rationale. Exact amounts retain original decimal strings and currency; ERP observations may use fixed scale while proposal values are canonical. No binary amount arithmetic or inferred tax/quantity defaults were introduced. Visible labels, form-order linked errors, specific inline constraints, a UTF-8 reason limit and immutable review precede submission. The form exposes all document parties and keeps currency/type separate.

Proposal, independent confirmation, revocation and internal ERP preparation remain distinct. Confirmation is not invoice gross, tax policy or final ERP approval. Preparation checks remain packet-scoped; owned-key admission/capacity/source coverage are rechecked on submission. Historical observation never settles an unknown operation. Identical resend retains the original target, packet, reason, revision and request identity. Fresh-HTTP recovery requires the same owned preparation key, document/digest and original actor under current checks. A successfully recovered owned key suppresses obsolete retries/leave warnings while its original unknown attempt remains explicitly historical.

Attempts remain visible outside selected details. Recorded receipts survive failed refresh. Request IDs and receipts use separate LTR-isolated rows in RTL layouts; replay is separate from the receipt hash. Explicit reauthentication invalidates advice without automatically resending. Browser document reload discards local attempt details; a new login discovers server history instead of claiming to reconstruct the original request envelope.

# Actual authenticated journeys

TestDocumentActualScreenBrowser starts the ordinary sample service on an ephemeral loopback listener after explicit synthetic authority/candidate setup. It requires an initially empty real runtime document adapter. Node launches the actual React app in Chromium with isolated sessions; credentials pass only in transient process environment. The server read-back requires exactly one document and one owned preparation with net 15.00, tax 1.00, quantity 5.00 and no external ERP commands. It checks confirmed or revoked lifecycle according to the scenario. Failure artifacts contain fixed stage/category labels, not raw authentication/request diagnostics.

- Normal journey: explicit proposal, independent second-account confirmation, actual preparation, a lost successful response, selection/navigation changes and byte-identical retry returning the original receipt. The expanded EN/KO/AR1440/1024/390 matrix covers blank fields, validation, populated proposal review, unknown and recorded results. Additional cases cover a clean injected proposal refusal, pending, partial noncanonical/mismatched/over-byte-limit inputs, unavailable history and delayed context. The latter failures/delays are explicitly injected browser transport conditions; server financial effects remain real.
- Fresh-login recovery: a server after-prepare interruption leaves an owned ledger effect without a recorded receipt. Another actual session for the same principal discovers history without local attempt memory, inspects matching-but-unsettled observation and submits a new HTTP identity with the exact original owned preparation key/document/digest. No replacement preparation is created.
- Reauthentication: the synthetic clock advances sixteen minutes after the actual preparation. The original retry is refused for expired recent authentication, the user explicitly reauthenticates through the real password dialog, and the unchanged original request then returns its recorded result. The harness verifies no automatic retry at dialog completion.
- Permission loss: the real prepare grant is revoked after the ledger effect. A denied identical retry retains the original unknown outcome. Denial is not described as proof of nonexecution.
- Hold-safe revocation: the service enters a real hold after preparation. The independent confirmer uses the real screen to revoke document evidence while the owned preparation and its exact amounts remain recorded.

Normal final verification includes actual computed font, neutral-border and bidirectional viewport/controls checks, not screenshot counts alone. Keyboard assertions cover visible summary focus, proposal/action Edit restoration and preserving a deliberately moved focus during pending completion. The delayed context check awaits the held response body, route fulfillment and rendering before reselecting and asserting no restored form. Historical refresh failure removes rows while preserving recorded results.
