# Outcome and ownership

HYB-311, machine:mac_mini, 2026-11-25. This document proposes a rule inside the retention register and asks for independent design review before any code changes. It concerns what protects against billing the same input twice, so the review covers billing integrity and data retention. It changes no amount and no permission. One read gains values; no command is added.

Requirements: HB-21 (no double billing, a mandatory gate), RET-06 (`docs/planning/v1.16/retention-access.md:123`: after the detail and the duplicate registry expire, a past input is not billed again automatically), the retention class row for claims (`retention-access.md:75`: the minimal record is kept separately; deleting the original must not allow billing again), `retention-access.md:100` (material whose duplicate registry expired is held as input outside the replay period and never approved as new; a duplicate key is not kept for ever without a basis), and the P04 specification (`docs/ui/screens/P04/spec.md:35-37`, the dependency list names the minimal claim reference). The trace of 2026-11-17 found no such rule and classified the item as deferred to the billing claims work (`docs/reviews/HYB-301-trace-classification/report.md:218-228`, item row `:324`).

# Facts read on main ee9a795

1. A register entry is an artifact with an identifier, a class, tenants, an anchor time and stores (`modules/retention/types.go:106-112`). It carries no content digest and no business key. The classes are source, final, claim, identity, conversation, temporary and projection (`types.go:21-27`).
2. A reference has a kind, `Requires` or `Mentions` (`types.go:29-30`). Only `Requires` protects: the artifact it points to cannot be deleted while the artifact it comes from exists (`records.go:124-127`, `changes.go:111-121`). References are written by the system actor only (`records.go:103-129`).
3. An artifact is left out of a deletion when a hold covers it, when something requires it, or when it is not due; it is due when its class has a policy and the anchor plus the period and the grace has passed (`changes.go:43-50`, `:111-121`). A class without a policy is never due.
4. A deletion goes through a plan that one person proposes and another approves, then chunks that a worker leases. The exclusion reasons are checked when the plan is applied and again when a chunk is leased (`changes.go:136-190`, `runs.go:95-108`); just before each deletion the worker asks `Proceed`, which checks holds only (`runs.go:234-248`). A store's report of a deletion is recorded as a fact whatever the artifact's outcome was (`runs.go:159-176`). An artifact is deleted when every one of its stores reports deletion (`runs.go:206-228`); with some stores deleted and not all it is damaged (`runs.go:191`). For each artifact the register can tell whether the backups of every store have expired past that store's deletion time (`complete`, `runs.go:294-301`); for a store that was never deleted that test is vacuously true. A run is complete when that holds for its artifacts and none is failed, deleting or damaged (`runs.go:338-346`); a run with one failed artifact therefore never completes. The command that records a backup expiry is not connected to the service (`apps/api/server/retention.go:678`).
5. A deleted artifact stays in the register as deleted, with a tombstone that carries a sequence, the artifact, its class, the run and the time (`types.go:236-242`, `runs.go:228`, `reads.go:81-104`). Registering a deleted identifier again is refused (`records.go:46-47`).
6. The claim class is used nowhere but in the class list (`types.go:23`, `:91`). No rule ties a claim artifact to a source. The sample data registers one claim artifact and no claim policy, so it is never due (`apps/api/server/retentionseed.go:314`, `:401-403`); a claim policy can be approved through the screen (`apps/api/server/retention_commands_test.go:108`).
7. Nothing but the sample data and tests registers artifacts, writes references or runs the worker; no deletion in the register removes data in another module; no command proposes a deletion plan (`retentionseed.go:362-398`, `retentioncmds.go:15-27`, `docs/ui/screen-binding-register.md:273`).
8. The claims module, which refuses a second application for the same contract, component and period, is not served: nothing imports it (`modules/claims`, no importer). It holds a source only as an opaque identifier and never deletes anything (`modules/claims/types.go:102-125`, `reserve.go:88-139`).
9. The intake and normalization modules key by identifier and report, but do not refuse, the same bytes under another identifier (`modules/intake/manifest.go:65-68`, `:103-124`). The file receipt registry of the FOCUS import keeps a deleted receipt's row, so the same file is still answered as a duplicate (`modules/focus_import/receipts.py:27-31`, `:217-231`).
10. The retention module imports the standard library only, and a test enforces it (`modules/retention/source_test.go:41-45`).

# What the gap is

With fact 6, once a claim policy is approved and a deletion plan for the claim class can be proposed, the register would delete a duplicate-prevention record on its own age, whether or not the source it stands for still exists, and whether or not that source could still come back from a backup. That is the case RET-06 and `retention-access.md:75` forbid. What stops it today is only that no plan command and no worker exist (fact 7).

# Proposed rule

A third reference kind, `Guards`: "this claim artifact is the minimal duplicate-prevention record of that artifact". Written by the system actor like the other kinds.

- G1 shape. The artifact a guard comes from must be of the claim class; the artifact it points to must not be; the two must share at least one tenant, so that a guard is not written between artifacts of unrelated workspaces. A record shared by two workspaces that guards an artifact of only one of them still shows as guarding to the other; that tells it only that something the record guards is not gone, never what. Anything else is refused as invalid. A claim artifact may guard several artifacts, and an artifact may be guarded by several claim artifacts. A guard, like a requirement, cannot be written while either side is being deleted, damaged or deleted. Note the direction: a requirement protects the artifact it points to; a guard protects the artifact it comes from.
- G2 the record outlives what it guards. A claim artifact is left out of a deletion, with the new outcome `guarding`, while any artifact it guards is not gone. An artifact is gone when it is deleted (every store reported deletion) and, for every one of its stores, the backups have expired past that store's deletion time. Gone is decided for the artifact, never from the state of its run. Consequences, all on the keeping side: a damaged artifact is not gone; an artifact in a failed or stopped run that is never retried is not gone; while no backup expiry is recorded for a store, nothing in that store is gone. Gone cannot be undone: a deleted artifact stays deleted, a backup expiry cannot move backward (`runs.go:287-288`) and the identifier cannot be registered again.
- G3 the period runs from the deletion. While any artifact it guards is not deleted, a claim artifact is not due. Once all are deleted, it is due when its class policy's period and grace have passed since the later of its own anchor and the latest time at which an artifact it guards was deleted (the time of that artifact's last store report, which is its tombstone time). The record is therefore kept until the later of that due time and the moment the last guarded artifact is gone. The period of the claim policy is thereby the replay period of `retention-access.md:100`. A claim artifact that guards nothing is due as today. Every place that derives a due state or a due time from the anchor uses this effective anchor: the due test (`changes.go:44`, `:49`), both sides of the impact of a policy change (`changes.go:72`), and the standing given to other modules (`exports.go:38`, `:45-47`). A due state can now move later when a guarded artifact is deleted after the claim artifact was put in a plan; the check at lease time then releases it as not due or guarding.
- G4 no silent removal of a guard. A guard is never removed. When the guarded artifact is deleted the guard stays and G3 applies.
- G5 after the record is deleted. Nothing new: the tombstone stays, and registering the same identifier again is refused (fact 5). While the register's memory lasts, a consumer that asks about a past input gets "deleted" and must hold the input as outside the replay period (`retention-access.md:100`). The register does not approve or refuse billing; it gives the answer that the billing side must honour. Keeping the tombstone is the kept deletion record of `retention-access.md:98`, not a duplicate key kept without a basis. The register is in memory only, so after a restart the answer is lost with everything else; persistence is not part of this ticket.
- G6 where the reason is checked and in what order. Held, then guarding, then required, then not due. The reason is checked wherever the others are: when a plan is applied, when a chunk is leased and on retry, in the preview of a plan (`reads.go:58-68`, which gains a guarding count), in the impact of a policy change (the module's impact view gains a guarding count beside held and required; like those two it is not part of the reviewed digest, so a guarded source becoming gone between review and approval does not change the reviewed impact, while a guarded source being deleted does, because the record's anchor moves), and in the standing given to other modules (`exports.go:31-52`).
- G7 what the property is about. The register authorizes deletions; it records what stores report. The property to hold is: the register never authorizes the deletion of a claim artifact (never marks it deleting at a lease or a retry, and never answers `Proceed` with yes) while an artifact it guards is not gone. A store that reports a deletion it was not authorized to make is recorded as a fact, as today; refusing such a report would change the meaning of `Report` and is not proposed.

What the rule deliberately does not do:

- It does not make a guard mandatory for a source. The register cannot know whether a source was billed. A billed source is protected through the requirement from its final document only while that document exists; after the final document's own period the source can be deleted with no record unless a guard was written. Writing the guard for every billed source is the duty of the billing claims producer when it is served, and the open point for the owner below is exactly this remaining exposure.
- It does not detect the same content under another identifier. The register has no content key (fact 1); that detection belongs to intake (fact 9) and is not part of this ticket.
- It does not keep a duplicate key for ever: G3 ends the record's protection after the approved period (`retention-access.md:100`, second sentence).

# What stays blocked

The rule is real in the register and reachable through its interface, but nothing in the service writes a guard except the sample data, because the producer of billing claims is not served (fact 8), the deletion worker does not exist (fact 7) and the recording of backup expiries is not connected (fact 4), so outside tests nothing becomes gone. This ticket therefore cannot show an input that was received again and refused. It delivers the rule that the producer must use, the sample data that exercises it, and the screen's wording for the new outcome. The connection is stated as not built in the binding register and stays with the billing claims work (phase 6).

# Read and screen

- The retention read gains the value `guarding` in the two places where an outcome or a standing is named: the outcome of an artifact in a run, with its count, and the standing of an artifact. The standing order becomes: in a run, guarding, no policy, not due, held, required, so that a guarding record is shown as such even when its class has no policy. The count of excluded artifacts per store includes guarding ones (`retention.go:598-604`). No field is added: the impact shown on the screen has no held or required counts today (`retention.go:246-251`) and gains none. These are new values in existing fields of a public read, covered by the change review.
- The console's key lists and labels gain the value in three languages (`service/retention.ts:166-167`, `live-codes.ts:25-33`, `:72-81`); today an unknown outcome key is dropped from the counts and an unknown label is shown as "Unknown".
- The sample data gains a guard from the sample claim artifact to one source of the first sample run, written before that run's first lease, since a guard cannot be written once the source is being deleted (G1). No claim policy is added to the sample data.
- Copy goes to the ui-designer review; the owner alone accepts the screen.

# Steps

1. Module: the reference kind, G1 to G6, tests including a property test of G7 over sequences of plans, leases, retries, stops, reports, holds and backup expiries, with runs that fail or stop (policy changes are covered by example tests only), and tests that the period is counted from the deletion. Independent change review for billing integrity and data accuracy.
2. Server and console: the sample guard, the read values, the label, the binding documents, a rendered check of P04. Independent change review; ui-designer review of the wording.

# Assumptions and open points

- Assumption: the replay period is the claim policy's period plus grace, counted from the deletion of the guarded artifact. The planning text names a "re-import allowed period" without a value; the value is whatever claim policy the installation approves, in line with the owner's direction that open values ship as changeable settings.
- Open for the owner: whether a claim policy must exist before any source deletion plan can be approved. Today no claim policy means the record is never due, which is the safe side, so nothing forces the question now.
- Not verified: behaviour on operating systems other than the development machine. The register is in memory only; persistence is outside this ticket.
