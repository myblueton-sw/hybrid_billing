# Shared read boundary

Three nonmutating commands use existing console-only, actual-human/nondelegated ViewCost on synthetic_document_evidence/document_evidence before lookup: document_evidence.context, document_evidence.history and document_evidence.advice. They require no mutation key, expected revision, rationale or step-up; existing authentication and CSRF rules remain. Resolve validates only workspace and target syntax. Unsupported runtime/SeedNone refuses. Projection failures return no fields. Normal command results supply the current global revision for a later mutation; advice never authorizes it.

All projections retain the existing minimum seventeen-field/2000-byte capability and per-value min(4096, configured limit). A read fails rather than truncates an oversized field. No read inserts documents, owners or ledger submissions, settles uncertainty, consumes financial approval or advances the server revision.

# History contract

Target is the owned financial request ID. Required input: digest (request digest), kind (documents or preparations). Optional after and snapshot must either both be absent or both be present. First page resolves current revision; subsequent pages require snapshot equal to the current resolved global revision, otherwise evidence_stale. This is restart-on-change pagination, not retained snapshot storage. after must be an actual matching row ID in the sorted result, preventing arbitrary cursor skipping. Page size is ten.

Seven fixed string fields: mode=synthetic, request, request_digest, kind, snapshot, next (last returned ID when more remain; empty otherwise), current_eligibility=unchecked. Up to ten row_00 through row_09 JSON values carry rows in ascending ID order. Empty results have no row fields and empty next. Rows are never grouped into an unbounded array.

Document rows contain document, digest (proposal), recorded_state, proposed_by and proposed_at. Preparation rows contain preparation, document, document_digest, actor and recorded_receipt; empty recorded_receipt remains unresolved. They do not claim current ledger observation. The existing dedicated inspections supply complete packet and ledger observation after selection. Preparation associations come only from exact retained proposal digests belonging to the selected request, never inferred names or candidate equality.

Validate the owned historical request and exact digest, then validated retained document records within the workspace. Include pending, confirmed and revoked documents. History remains readable under hold, current producer staleness and revoked mutation permissions, while current Cost permission stays mandatory. For every preparation owner in the workspace, require exactly one validated document with the same proposal digest. Require the owner map key to equal its submission key, valid actor and receipt shape (empty or 64-byte digest), and the associated document to match its own valid workspace/request binding before filtering to the selected request. Valid owners of another request must not cause refusal. Orphan or duplicate proposal-digest associations fail the entire history read, even if their request cannot be identified; they never silently disappear. Corrupt retained associations fail closed; foreign workspace records never appear. A missing request and mismatched digest refuse without exposing other requests. No filtering by current actor: authorized workspace Cost readers must be able to find another proposer's documents for independent confirmation. Existing bounded stores cap scans at one hundred entries.

# Form context contract

Target and digest identify the owned financial request. Context requires current financial approval and exact owned candidate provenance; history stays independently available when context refuses. It projects only rated line identifiers/rules/kinds/amounts, currency, total, customer, period and document organization identity. It never returns supplier costs, raw source rows, input evidence or pricing policy details. Ten-line revision-bound pagination follows the history cursor rules, using original line IDs and unique deterministic ordering. The header binds request/candidate digests and profile synthetic_individual_net_v1.

Available ERP connection/product/tax identifiers must come from explicit sample runtime configuration and be read back from the actual ledger, including customer mapping and survey. They are selectable facts, not default quantity/tax/unit/evidence. There is currently one named synthetic connection/product/tax combination; do not invent a general connector inventory. Refuse unsupported profile/shape, duplicate or excluded lines, non-positive/non-rated charges, incomplete source coverage, currency/organization/period mismatch and stale producer data. The packet builder and mutation still revalidate all facts independently. Exact decimal amounts remain strings.

Context has six fixed string fields: mode=synthetic, request, request_digest, snapshot, next and header. The header JSON contains candidate, candidate_digest, profile, currency, total, customer, period, organization (the complete DocumentKey), and erp (connection, product, tax_code, scale). Each row_00 through row_09 JSON object contains line, rule, kind and amount. The complete header is repeated unchanged on every page; all header/row values are preflighted without truncation. No editable document field has a default.

Extract a read-only candidate shape validator from documentSubmission for the existing immutable candidate/request checks: matching candidate/digest/document/workspace/currency, external invoice organization path, complete calendar month, exact input/normalized/rated line bijection, no excluded lines, unique original source identities, rated positive amounts at the connector scale, and exact total. It accepts no quantities, units, tax or declared document totals. Both context and documentSubmission call it, with identical existing refusals preserved. Never invent placeholder quantities or zero tax to call documentSubmission. Context reads named connector/mapping/survey facts and validates currency/entity and supported preparation capability; it does not claim document readiness or reserve source coverage.

# Action advice contract

Target is document ID; required digest is its retained proposal digest. After Cost authorization and historical document validation, return separate propose/confirm/revoke/prepare permission results and separate document readiness findings. Confirmation advice checks distinct proposer, original proposer authority, current financial/ERP evidence and pending state. Preparation advice checks confirmed state, current evidence and hold; the exact requested preparation key still requires mutation-time ledger checks. Revocation advice allows pending/confirmed records under hold and stale producer evidence. Terminal history remains visible. Use explicit ready, denied, unavailable or inapplicable states with bounded refusal codes; do not collapse dependency failures into permission denial. Advice must not call Prepare or reconcile, and cannot claim packet admission or a preparation key is reserved.

Advice fields are mode, document, digest, current_eligibility=advisory, permissions and readiness. permissions is a JSON object with propose/confirm/revoke/prepare entries, each {state, code}: allowed with empty code; denied with permission_denied or unauthenticated; unavailable with authority_unavailable or dependency_unavailable. Only current action rights determine these entries. readiness is a JSON object for confirm/revoke/prepare, each {state, code}: unchecked when the corresponding permission is not allowed; inapplicable for terminal/incompatible state or self-confirmation; unavailable for unavailable dependencies; blocked for hold, stale evidence or withdrawn prerequisite authority; ready only when the specified checks pass. Precedence is permission, lifecycle, self-confirmation (confirm only), hold (confirm/prepare), original proposer authority (confirm only), current financial and ERP evidence. Revocation readiness does not consult producers. Preparation ready means packet prerequisites only; a seventh field preparation_scope=packet_only_key_capacity_and_source_coverage_unchecked states the excluded exact-key checks. Mutation-time permission and all prerequisites remain authoritative. No propose readiness is asserted from an existing document; context supplies new-form facts separately.
