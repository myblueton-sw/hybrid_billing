# Continuous product terminology review

The owner requires continuous technical-writing review of service terminology. Apply this rule to every new or materially revised screen and user-facing copy change, including menu, title, tabs, fields, actions, states and help.

- Assign technical-writing responsibility before implementation. Use the local tech-writer skill and a separate read-only TW review for a new screen, menu rename or financial/permission meaning change. A role-based AI review is not a human practitioner or native-language approval.
- Start from the planning purpose and actual producer/consumer data contract. Select one preferred term per concept in the [product glossary](../../docs/ui/terminology/product-glossary.md). Record the definition, preferred KO/EN/AR labels, evidence, forbidden implications, affected screens and review boundary.
- Keep canonical screen IDs, routes, fields, enums and API identifiers stable when changing display labels. Explain a necessary specialist alias in help or mapped-field views; do not make internal implementation jargon the only user label.
- Preserve financial meanings: billed versus effective cost, source versus recognized cost, consumed versus pricing quantity, declared inclusion versus verified duplicate, browser draft versus server revision, source finalization versus financial approval, FOCUS account scope versus legal entity.
- Check affected existing screens and error/empty/loading copy for the same concept before QA. Search for superseded display terms and update active copy, menus, titles, tests and screen records together; preserve original planning evidence and canonical contracts.
- After rendering, have TW inspect the changed wording in context. Record inspected KO/EN/AR variants and unresolved native-language or domain questions. A build or machine translation cannot certify terminology.
- Routine copy corrections proceed within the owner's authorized scope. This rule adds no new approval checkpoint, deployment permission or automated owner FIX.
