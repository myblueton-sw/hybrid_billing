This is a proposed implementation contract, not an activated customer policy, deployed command or completed screen. Retain the [Claim/numeric contract](claim-and-numeric.md), [PC-01/02 financial sequence](inputs-pricing-and-erp.md), [SP-01–07 cost and selling obligations](source-pricing-and-cost-obligations.md), [AUTO-01–10 pricing workflow](../../reviews/HB-42-auto-pricing/requirements.md) and [shared command envelope](../commands/planning-actions.md). # AP-01: required profile and frozen pool

An allocation profile is a versioned rule definition. A pool snapshot is one complete application of it to fixed evidence. Approval of the definition does not approve a pool's amounts. The names below define logical fields, not deployed storage or API names. Unknown required values remain absent with reasons and prevent activation; zero and not-applicable are explicit evidenced values, not substitutes for unknown.

| Field group | Required content and validation |
| --- | --- |
| Profile identity | Stable profile ID, immutable revision, purpose (`cost_attribution` or `benefit_attribution`), owner and rationale, effective interval/timezone, policy evidence and independent expected-case references. A commercial selling concession uses its own selling policy; it is not inferred from procurement EDP. |
| Authority scope | Installation/workspace, issuer/responsible organization, supplier agreement/account scope, permitted recipient relationships and internal bearer scope. Server resolves authority from current identity/grants and registered relationships, never a caller tenant field. A pool cannot cross an unapproved responsibility boundary. |
| Source evidence | Eligible source manifest/revisions, authoritative amount basis (billed, effective or explicitly defined pro-forma), currency, charge and billing intervals, source economic-component identities and comparison/confirmation evidence. Original source amounts are immutable. Do not sum incompatible bases or currencies. |
| Benefit representation | Stable benefit/obligation identity, origin and agreement evidence, eligible/excluded dimensions with reasons, amount and sign semantics, representation (`embedded_in_basis`, `separate_component`, or unknown), exclusion/stacking group and coverage identity where applicable. Difference between list and net alone is not EDP provenance. |
| Pool composition | Stable pool ID/revision, source component membership and coverage/split lineage, original signed total, accounting period, complete canonical target manifest and membership effective intervals. Detect duplicate or overlapping source economics across pools, not only duplicate rows/targets. |
| Target basis | For every included canonical target ID: recipient kind (customer relationship or explicit internal bearer), eligibility reason, evidenced exact nonnegative weight and unit, weight/source revision. Fix basis (capacity, usage or reservation), full denominator and any required proration/split evidence. Excluded recipients are recorded separately with reasons; they are not zero-weight members. |
| Idle/unattributed treatment | Explicit approved idle bearer and amount/weight treatment; separate unresolved attribution status. An approved internal residual bucket may preserve cost reconciliation but cannot silently authorize customer charging or final allocation of unknown coverage. Missing mapping/weight is not zero. |
| Arithmetic | Approved numeric profile ID/revision with all bounds, allowed signs, input scale/magnitude, aggregate/intermediate bounds, quantum, rounding stages/mode and algorithm/version. `largest_remainder_v1` uses the existing exact whole-pool contract; caps/minima are unsupported by that algorithm. No defaults from DB types or source ingestion profiles. |
| Selling linkage | Explicit separate selling policy revision or evidenced `internal_only`; pass-through/unused-burden terms, fee eligibility, exclusion granularity and ordering references where applicable. Cost attribution alone never creates a billable selling component. FX and tax use separately approved PC-01 inputs at their defined stages. |
| Approval policy | Versioned permissions, independent approver mapping, scope/ceilings, any validity window and evidence-bound warning rules. A valid named finance owner approves actual policy values. Generic installation administration and AI recommendations cannot activate them. |

The pool snapshot materializes the profile and all referenced revisions; referencing a mutable “latest” value is insufficient. Every component either belongs once to the declared allocation scope or has an evidenced approved split with non-overlapping coverage and conserved source cost. A host's full cost cannot be included again in each VM, nor the same full equipment cost in both CPU and memory pools. Unknown overlap or source replacement lineage blocks the affected pool.

For effective-dated moves or mid-period changes, pin registered membership intervals and the approved proration rule before calculation. A later organizational move cannot reset allowance/benefit identity or rewrite earlier allocations. Missing historical evidence blocks exact final allocation; any permitted provisional statement remains separately labelled under SP-05.

# AP-02: calculation and benefit separation

1. Verify source eligibility/completeness and currency/basis before constructing the full pool. Supplier reconciliation precedes customer selling. BilledCost and EffectiveCost are not required to equal in the same month.
2. Resolve benefit representation and economic identity. When supplier net900 already contains benefit100, keep900 as that net basis; explaining/attributing100 creates no second cost deduction. A separate benefit component can adjust a compatible basis only with agreement evidence and explicit non-duplication proof. Unknown representation blocks the affected calculation.
3. Freeze the complete eligible target manifest and denominator, including approved non-customer idle treatment. A display filter, page, worker partition or selected invoice batch never defines the pool. A deliberate scope change creates a new profile/pool revision, requires full eligibility validation and review, and cannot reset finite-benefit coverage.
4. Calculate with bounded exact arithmetic and the selected algorithm. Validate raw input bounds before normalization. Weight conversion to common integers and intermediate products must fit the approved resource/numeric limits; overflow rejects rather than changing precision. Stable target-ID ordering uses a versioned canonical byte encoding and bytewise order, never display labels, locale collation or worker order; the implementation contract must fix this encoding before execution.
5. Record the original pool total, quantized target, signed rounding component (`original minus quantized`), exact denominator and per-target amounts. Require signed recipient sum = quantized target, with original = recipient sum + rounding component. No hidden tolerance or arbitrary last-recipient balancing. Failure leaves a blocked candidate and publishes no partial manifest.
6. Publish cost/benefit attribution as its own immutable full manifest after the appropriate scoped approval and revision checks. Separately derive selling components under the approved selling method/order. Never add internal allocated cost and external selling price into one financial total. Customer selling approval and issuance are separate gates.

An attribution of an embedded procurement benefit is explanatory; it does not consume a second grant. A genuinely finite benefit used by a selling application follows the authoritative Claim/coverage contract. Preview, result computation and attribution publication do not reserve or consume it. The later economic application records the approved original benefit/coverage identity, even after retries or source revisions. Procurement EDP does not automatically imply the customer's product-discount exclusion group.

# AP-03: approval subject and authoritative transitions

All proposed operations use the existing command envelope: server-bound authority, expected revisions, canonical payload digest, initiating principal, scoped idempotency and authorized result read-back. Operation labels below are contract concepts, not new registered command IDs or deployed HTTP endpoints. Concrete command registration and role mapping are implementation prerequisites.

A server-created approval subject fixes a versioned canonical payload containing purpose/layer, profile revision, authority/relationship scope, eligible source and independent comparison/confirmation evidence, economic component and benefit identities/representation, complete pool/target/weight/denominator data, effective intervals, numeric/algorithm/ordering revisions, exact output manifest and rounding component, selling-policy linkage where relevant, and resolved warning evidence/acknowledgments. Persist canonical content and digest together; compare content/registered identities to detect collisions or ambiguity. The client cannot provide an authoritative total, passed check or approval subject.

Profile decisions bind the complete definition and its expected-case evidence. Pool-amount decisions bind the complete calculated subject. Each decision separately retains actor, current authority context, time, rationale, permission/ceiling policy and decision revision. A whole-pool amount approver must have authority to inspect/approve the complete financial scope; a customer-scoped approver cannot stand in for that role. Customer selling approval can cover a separately authorized subset without changing the underlying pool.

| Operation / transition | Preconditions at authoritative commit | Result and failure recovery |
| --- | --- | --- |
| Save profile draft | Current scoped edit authority and expected draft revision | New versioned draft, with unresolved fields visible. No activation or amount approval. |
| Approve/activate definition | Complete field/evidence validation, current independent finance approver within ceiling, effective policy and expected revision | Immutable decision and effective profile revision. Changes require a new revision/approval; no inherited approval for changed content. |
| Build/compute pool candidate | Approved applicable profile, eligible complete source, current compute scope, all numeric and coverage guards | Deterministic candidate and calculation evidence or explicit blocked/failed job. Completion does not approve amounts or consume benefit. |
| Approve pool amounts | Full subject reconciled, required comparisons passed, warning decisions current, independent approver within whole-pool ceiling, expected pool/source/policy/authority revisions | Immutable approval tied to exact subject. Self-approval by preparer is rejected under this proposed allocation approval policy. No issuance or grant consumption. |
| Publish attribution manifest | Same subject and approval still eligible; current publication authority; expected publication/dependency revisions, all current holds and guards | One authoritative pointer to the complete immutable manifest. Stage/validate artifacts before atomic metadata publication; failed publication exposes no partial financial result. |
| Reserve/apply a finite selling benefit | Separate approved selling amount/coverage, current authority and all Claim preconditions | Claim transitions govern reservation, dispatch pinning, consumption, release and reversal. Attribution publication alone supplies none of these effects. |
| Read/replay a result | Current scope/field authority, including cached/exported/prior idempotent results | Return only permitted evidence. Same identity/payload replays the existing operation; changed payload conflicts, and a new request key cannot bypass economic identity protection. |

Each authoritative transition rechecks current grants, role ceilings, applicable authority epoch, policy/approval eligibility and every mutable dependency against expected authoritative revisions within its commit boundary. An earlier preview or queued-job check is insufficient. Use existing authority/submission ownership; do not create a second financial authority. Physical transaction/fencing design and concurrent revocation proof belong to the authority implementation ticket. If current dependencies cannot be established, fail closed.

An affected input, source confirmation, membership, weight, basis, sequence, arithmetic policy, warning, scope or result change invalidates the pending subject and its amount approval. A newer approved definition effective only in a disjoint interval need not invalidate unrelated pools, but non-impact requires explicit dependency evidence. Incomplete dependency traversal blocks possibly affected publication. Revocation or authority outage prevents new actions and disclosure without rewriting historical approvals. Already-published or issued artifacts remain immutable; correction/reconciliation follows linked history rather than overwriting it.

External dispatch timeout or worker expiry leaves the original obligation pinned/unknown. Read back/reconcile the same external identity; do not blindly retry, release it or construct new eligibility. Confirmed effects require governed reversal of the original per-recipient coverage/application. Replacement requires explicit authorized linkage; today's weights do not determine historical reversal amounts.

# AP-04: connected operator review journey

This specifies content and actions to bind into the existing pricing portfolio, trace, exceptions, activation and history views (AUTO-04–09). It does not deliver rendered screens or modify frozen v10 pages.

| Step | Operator sees | Action and next state |
| --- | --- | --- |
| Choose period and pool | Responsible organization, source basis/currency, eligible revision/as-of, profile version and distinct draft/blocked/review/published counts | Open a permitted pool. Loading and unavailable authority are explicit; no pool is an empty state, not a zero amount. |
| Complete definition/evidence | Missing policy fields, benefit embedded/separate status, source comparison and eligibility reasons | Save draft or request evidence from the responsible workflow. Unknown required evidence keeps activation unavailable with a specific reason. |
| Inspect complete calculation | Original and quantized totals, rounding difference, included/excluded targets, weights/denominator, idle/unattributed amounts, source-component overlap findings | Open permitted line evidence. Search/filter retains a visible full-pool context; a subset never recalculates shares. |
| Compare revisions | Old/new per-target attribution and separate selling effects, changed evidence/rules, newly blocked targets, all amounts separated by currency/basis | Recompute after resolving blockers; a changed subject requires renewed review. Comparison uses the same source inputs or explicitly identifies the source difference. |
| Submit and independently approve | Exact selected subject, whole scope, exceptions, warning reasons and action effect | Submit for review; an authorized independent reviewer approves or rejects with rationale. Approval button text identifies pool attribution, not invoice issuance. |
| Publish and inspect history | Publication status and immutable revision; selling approval, finite-benefit application and issuance shown separately | Publish when guards still pass; inspect history. A publication race shows conflict and requires reinspection. Unknown dispatch offers reconciliation, not a blind retry. |

Blocked, rejected, stale, technical failure and external unknown are distinct statuses with reason, owner, evidence timestamp and next permitted action. Technical retry resumes the fixed operation only when safe; changed evidence creates a new candidate. Bulk selection captures an explicit target manifest and applicable partial-activation policy; blocked members cannot silently inherit a new policy. Publication remains complete per economic pool, even when separate downstream customer operations proceed independently.

Use text as well as color for states; retain keyboard access, focus after errors and readable field-level validation. Private source costs, other recipients, denominator details, internal approval history and margin remain operator-only unless an explicit disclosure contract permits specific fields. Customer output uses authorized selling explanations from the unchanged complete result, never a recalculated visible-only denominator. Permissions apply to counts, filters, exports and links as well as rows. An unavailable backend must be labelled unconnected, never shown as a successful calculation.

Durable overlap, atomic publication, lost-response replay and revocation require actual authority integration tests.

# Implementation readiness and unresolved decisions

The first calculator implementation may use an explicitly synthetic complete profile to validate arithmetic and bounds; it cannot activate real terms. Before production activation, supply actual agreement benefit provenance, eligibility/basis/weights, private pass-through and idle-bearer terms, effective/proration rules, numeric/resource limits, canonical ID encoding, named approval roles/ceilings and acceptance evidence. Approval-policy independence above is a proposed product rule to implement and validate, not a claim those roles already exist.

Pure calculator output is a candidate only. Authority implementation must register concrete commands and prove commit-time guards, stable economic identity, immutable complete manifests and Claim orchestration. Connected screens and customer disclosure then require browser/accessibility and authorization QA. No schema migration, language/database selection, provider compatibility certification, live pricing, issuance or deployment is implied. See the [work brief](../../work/HB-57-allocation-profile/brief.md) and [verification record](../../work/HB-57-allocation-profile/verification.md).
