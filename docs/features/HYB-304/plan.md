# Common contract to review before code

1. Authorize first and recheck on every page/count/detail; bind current session, canonical user/workspace and disclosure scope. M02–M04 retain installation administration; M05 remains self-only. Query parsing must not leak unauthorized object existence or counts.
2. Parse a per-list allowlist with bounded UTF-8 search, exact enums/IDs/dates, one value per key and bounded page size. Reject unknown, duplicate, malformed, unsupported or cross-workspace values; never silently ignore them. Search excludes secrets, raw identity proofs, tokens and submitted reasons.
3. Choose one documented stable order per collection, with canonical ID tie-breaker. Cursor continuation binds the list, normalized filters, order, current caller/workspace, reference time and relevant generation/revision. Detect changed/expired/invalidated continuation and return the existing safe409-restart convention where applicable. No offset masquerading as a stable cursor. Reuse the HYB-294 two-segment ordering only where a list genuinely has two distinct ordered populations; do not reuse its login/departed segments for unrelated lists.
4. Bound server scans and emitted rows independently. Avoid copying every domain row before applying the budget. Add indexed/bounded module reads where existing APIs return entire registries. Counts are exact only after complete authorized evaluation; otherwise represent lower-bound/unknown/unavailable distinctly. Empty pages with continuation or scan exhaustion are not proof of zero matches.
5. Installation defaults that affect page/scan/cursor lifetime are configurable with bounds and settings provenance; use the existing AccessSettings/CLI/settings-row mechanism. Do not introduce unrelated monetary or retention defaults.
6. Browser query state follows canonical route/list scope; apply/clear, page size, next/previous and history restoration preserve normalized filters. Filter/workspace/session changes reset continuation and explicitly invalidate incompatible selection/preview. Late reads and commands cannot repaint another generation. A409 clears stale page/selection and offers a fresh query; it is not automatically retried as a mutation.
7. Keep each independent list independently paged. Summary reads and auxiliary pickers must stop returning the entire population too; a new paged endpoint alone is insufficient if the old screen entry still downloads all rows. Known-ID detail/command eligibility cannot depend on the current page having that row.
8. Full-scope actions must preserve a server-fixed target set, digest/count and generation; never redefine 'all other sessions' as 'other sessions on this page'. Operation-detail lists and held/not-included rows must also stay bounded. Existing one-session commands, independent-control/step-up, unknown-outcome locks and cleanup vs security-effect distinctions remain intact.

# First increment contract, revision after independent review

Independent reviewer `/root/hyb310_review` accepted the full scope inventory but returned implementation-readiness FAIL. Three findings: fingerprint-only reconstruction cannot preserve the confirmed set; login/registry presence alone cannot prove current canonical eligibility; paging only sessions leaves operation rows and page-derived eligibility unbounded/incorrect. The following contract replaces the undecided alternatives and passed revised independent design review before source implementation. The current server foundation and remaining work are recorded in [query progress](query-server-progress.md).

## Identity, rows and cursor

- Store/index sessions by the canonical user identity resolved when the authenticated session is opened, with its incarnation/epoch, workspace and caller session. A login string is not the authority key. Update the ordered per-owner index with every add/remove/deny/expiry cleanup; registry mutation and index changes are one lock-protected operation.
- Session queries use `GET /api/v1/me/sessions` with allowlisted `session=all|current|other`, `workspace`, `since`, `until`, `q`, `limit` and `after`. The bounded response uses `rows`, opaque `next`, normalized `query`, `reference_at`, `generation`, documented `order`, `count` certainty and `scan_stopped`; an exhausted continuation is explicit rather than inferred from an empty page. Filters: current/other/all, current permitted workspace and signed-in period (the meaning is explicitly signed-in time; recent access remains the separate HYB-306 history period). Search uses only the non-secret visible session handle and displayed timestamps. No raw verifier, cookie, CSRF token, network address or device fingerprint is searchable.
- Order current session as a separately identified row, followed by other sessions in signed-in-time descending/handle ascending order. Current-session inclusion and count are explicit; it never repeats across continuation pages. Current workspace is returned as the one supported workspace choice and any other requested value is rejected without object-existence details.
- Each row exposes effective state and permitted actions based on current denial/trust/membership/policy/expiry checks. Use Boundary.Peek or equivalent read-only checks; never refresh another session’s idle deadline while listing it. Registered-but-expired, revoked and unavailable evidence is distinguishable from an active session. Do not infer liveness from registry presence.
- Cursor binds normalized query/list/order, canonical owner/incarnation/workspace/caller, reference time, ordered-index generation and eligibility deadline. Bind it with the process-local integrity key; restart invalidates old cursors. Current admission is rechecked on every request, and the earliest relevant time-driven transition invalidates continuation even if no registry mutation happened. Invalid/foreign/mismatched references yield uniform safe errors before count/detail disclosure. Changed or expired continuation requires an explicit fresh query.
- `/me` carries identity/policy/current-session metadata and bounded recent-operation summaries; it does not carry every session or expanded operation row. Summary counts state exact/unknown/unavailable truthfully. Known-ID session detail/eligibility is an authorized read independent of the current list page, and must recheck the same owner/incarnation/workspace. UI commands cannot use page membership as proof of existence or eligibility.

## Frozen selection and operation lifecycle

- The user explicitly opens “Review all other sessions in this workspace”; it is distinct from current-page selection and is unaffected by the list’s search/period/page filters. The confirmation states that full workspace scope and separately shows its exact count. No hidden change in target meaning follows a page/filter change.
- `POST /api/v1/me/sessions/selections` prepares a self-only, CSRF-protected transient view snapshot; it changes no domain authority and requires no rationale or financial approval. The API’s existing self-session route remains the authorization boundary. Every preparation/resume reauthenticates the current caller and enforces the same source scope. This use of a transient read snapshot outside the domain command registry is an explicit contract-review item, not an assumed workflow exception.
- Preparation returns a non-secret opaque reference bound to canonical owner/incarnation/workspace/caller, the frozen source generation/reference time and expiry. It stores the actual canonical handles and minimal preview metadata on the server. It never returns an unbounded handle array. Repeating a preparation request for the same source/query generation reuses the same live view; it does not allocate another copy.
- Build at most the configured scan budget per request using the per-owner ordered index. Return building/progress/continuation without an invented final count; no percentage. If the index or authorization/time basis changes during construction, discard the incomplete view and require a fresh preparation before any side effect. Seal only after the entire permitted source has been evaluated. Exact count/digest and paged preview then refer to the same immutable stored set, including truthful already-inactive/unavailable categories.
- A sealed selection is immutable: later additions are excluded and later removals remain recorded targets. Submit its reference, exact digest and count; no browser-wide handles. Require current admission and step-up, matching owner/incarnation/workspace/caller and unexpired sealed status before side effects. Compare the supplied fingerprint with the stored set, never reconstruct it from the latest registry.
- Under the existing domain/security lock, resolve replay of that exact retained reference before comparing live generations. Apply the existing security-deny/cleanup semantics to recorded targets; report already-gone targets and later arrivals separately. New sessions are never added to the confirmed set. Incompatible authority fails before effect. Do not reject a compatible set merely because a new unrelated session arrived, and do not claim cleanup completion from security-deny acceptance.
- One server-owned record owns the immutable selection and its eventual operation identity; transition it once from prepared to accepted/settled. Keep the original frozen targets/fingerprint for replay and paged results. Avoid a separate reconstruction cache that could silently widen a retried command. Operation summary contains authoritative totals; operation rows and not-included entries have separate bounded detail pages.
- Once expired/evicted, a selection reference cannot create a new operation or target set. An accepted operation replays from its retained record independently of subsequent live session generations; retained-operation eviction produces explicit result-unavailable and a current-state check, not automatic resubmission. Keep the legacy ≤64-handle request as a separate compatibility path; never truncate the new full-set path to64.

## Limits, settings and resources

Use the existing AccessSettings/CLI/settings-row mechanism with source/default/bounds. Proposed changeable defaults for review: page size50 (1–100), scan budget1000 (100–10000), view lifetime300seconds (30–3600), prepared views per caller2 (1–8), maximum targets per view10000 (64–10000, no larger than the existing global session capacity), and global retained record/reference budget50000 (256–1000000). Operation-detail page size shares the configured query page size. Existing operation retention of five records is preserved, separately identified from prepared-view capacity.

Global accounting covers building, sealed and accepted records together. Charge one unit per record plus one per stored frozen-target row, result row, not-included row and outstanding retry entry; each row has bounded identifier/time fields and at most the existing fixed eight cleanup items. Bound any additional strings/arrays at parsing/creation. Prepared-to-accepted transition transfers its existing charge and never resets it. Before the first security effect, reserve all additional result rows, the exact current not-included rows and the worst-case one retry entry per target under the same domain lock. Unused reservations are released after construction; accepted retries consume their reservation rather than allocating outside the budget. Startup validates budget >=1+3×maximum-targets, while actual admission still checks occupied capacity and not-included allocations.

Count capacity before every build append and seal/accept allocation. Abandoned building/sealed records release their charges only on explicit cancellation/expiry/removal. Settled operation eviction releases its immutable targets/results/not-included charges; completed retries release retry charges. Retain up to five operations per owner, additionally subject to global capacity: only settled oldest operations may be evicted under pressure, with an explicit result-unavailable response for later references. Active cleanup records and their minimal target/retry state cannot be evicted for admission, even after preparation expiry. Keep enough retained-operation identity to finish/replay active work. Accepted replay remains valid after preparation expiry while the operation record is retained. A record removed by retention/capacity can never recreate the operation on a repeated reference.

If capacity cannot be reserved without evicting active work, return an explicit recoverable limit/unavailable result before modifying any confirmed target. There is no partial security effect from admission failure. Every per-owner record and session-churn result consumes the same global budget, so per-owner five-record retention is not mistaken for a global bound. Manifest count always means recorded targets, with inactive/unavailable categories separate; it is not an exact active-session count. No source/retention policy, install authority or monetary setting is silently changed.
