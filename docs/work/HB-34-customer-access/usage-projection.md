# Profile and evidence

The initial profile `source-usage-v1` contains exactly service, quantity, unit, usage_start, usage_end and measurement_state. Quantity is an exact fixed decimal string or empty with state `missing`; measured zero is a decimal zero with state `source-reported`. This says nothing about actual versus estimated quality. Time is the original charge interval in UTC; no proration or invented finer resolution. Source service and unit values must map through explicit trusted profile dictionaries to approved public labels. Unmapped values fail closed, including rows outside the returned page. Null quantity/unit are represented explicitly, never numeric zero. No monetary or pricing field is permitted.

The trusted installation config binds installation, source name, source actor, exact company/tenant UUID, fixed source snapshot, start/end UTC, grain and profile revision plus approved service/unit maps. None is supplied as authoritative caller query input. Profile bytes receive a SHA256 revision, returned with safe page metadata. Replacing a gateway/profile requires invalidating affected subject grants through the existing versioned authority update before using the new configuration; this increment has no live profile-edit endpoint. Configuration is not proof of a real customer's commercial approval: runtime evidence uses explicitly synthetic labels and identities.

Basis: C02's permitted service/quantity/unit and period requirements; `usage-detail-lifecycle.md` separates purchase cost from customer amounts and requires fixed revision/basis; `access-and-trust.md` requires current grants and protected evidence. Response metadata says `usage-only`, currency `not-applicable`, `source-reported`, `exploratory-query-only`, fixed time range/snapshot/profile revision and bounded-page coverage. No raw batch/window/source locator, source role, account, raw missing-reason map, costs or hidden totals cross the Python bridge. Row references are opaque SHA256 values scoped by installation, tenant, source batch and ordinal.

# Source protection and protocol

Reuse `collection.query` and its existing PostgreSQL tenant/gate locks, local lifecycle coordinator lock, journal/checkpoint/mirror validation, revoked actor checks, source publication/slice digest verification and reader SQL credentials. Add an internal consumer callback executed before these contexts exit, receiving the journal, coordinator, authorized tenant context, selected slices and full selected rows as internal arguments. The consumer validates exact source installation/company/tenant/source/snapshot and builds only the safe page. Multi-tenant audience readers and archived slices are rejected for this profile. The source remains bounded by existing 10,000-row exploratory controls; this does not certify production-scale queries.

The underlying range selection uses delivery-window overlap, not row-time clipping. This profile additionally rejects any selected row whose original charge interval extends beyond the configured UTC range; it never prorates or silently removes it. The response identifies the selection as delivery-window overlap with contained charge intervals. All selected rows are checked for scope and approved service/unit mappings before the bounded page is returned, so page size cannot bypass a profile incompatibility.

The internal consumer has a preflight hook immediately after source snapshot validation and before any slice read. It verifies the trusted source bindings and requires every selected slice to be hot, preventing `archive.read` from running. Its final consume hook receives both the page and full selected rows under the same locks. Go revocation before the final authorization check invalidates the result; an update after that check is after linearization, even while the release handshake finishes.

Go installs a trusted subprocess command and immutable profile; only after current Go grant authorization does its reader start the Python bridge. Input and output bytes and elapsed runtime are explicitly bounded. Python emits a single safe `ready` envelope while source protections remain held, then waits for a `release` line. Go validates/copies rows and rechecks current authority through `customeraccess.Service.Query`, then requests release. Python acknowledges while still inside the protected consumer, exits normally and releases locks. Go returns data only after the acknowledgment and successful child exit. Early child death, extra output, malformed envelope, cancellation, timeout or failed acknowledgment returns no rows. Stderr and raw process/database errors never reach the caller.

The configured command must execute the Python bridge directly without spawning descendants or a shell. The bridge entrypoint does not spawn processes. Timeout termination/reaping covers that direct process; arbitrary wrapper/process-tree execution is unsupported. The test-only direct Python adapter changes local engine namespaces in process and likewise spawns no children.

The internal linearization point is the final Go authorization check while source locks are held. The subsequent acknowledgment proves the child remained in the protected consumer through that check; a failed handshake discards output. Source lifecycle changes serialize behind the existing coordinator lock and can be delayed by a slow read until the explicit runtime deadline. Go authority updates do not require the source lock; relevant updates before final authorization reject the result. Lock order is source locks then brief Go authority read lock; Go never holds an authority lock while starting/waiting for a subprocess. Cancellation kills/reaps the child and frees source resources. No source mutation, file output or durable customer package is performed.
