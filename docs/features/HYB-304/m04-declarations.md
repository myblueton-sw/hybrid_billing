# Chosen producer contract for review

A service declaration is versioned and keyed by authenticated canonical workspace/service ID, with purpose, owning organization reference and selected audience/scope pairs. Responsible owner remains the real identity.ServiceInfo.Owner. No organization is derived from the creator/owner. Missing legacy declaration is explicitly unavailable, not an empty allowlist or unrestricted scope. Stored declared references survive subsequent catalog/organization ineligibility for historical read-back; current eligibility is recomputed for writes and credential issuance.

The trusted catalog is explicit installation configuration, immutable for a running server. It contains audience IDs, actual recipient identifiers and named scopes with complete structured gate.Terms (action/kind/fields, workspace/customer/legal-entity/contract selectors and period). No actual recipient or scope is preinstalled by default. An empty catalog offers no selectable declaration or claimed access. A catalog fingerprint covers the entire normalized content; changed configuration/process keys invalidate dependent continuations. Published labels/IDs are operator metadata, not translated permission meaning. CLI configuration loading and bounded eligible catalog reads are required before the feature can merge; a Go Config field alone is insufficient.

Scope selection identifies an exact catalog audience/scope entry and does not mint a grant, link a service to ConsoleClient or loosen gate principal checks. A scope is valid only when its full Terms syntax, configured action/kind/fields and workspace are valid, with human-only approval and all installation-only actions excluded. Exact named customer/legal-entity/contract references require actual workspace-bound producer validation before a declaration is accepted; wildcard selectors are explicit trusted configuration, never missing-value defaults. A recipient identifier is explicitly supplied configuration, not a promise of a working external connection. No new outbound validation, token issue or customer access is performed by metadata validation.

Organization eligibility includes active workspace, active selected legal entity/internal unit and active legal-entity parent of an internal unit. Both existing Party kinds can own the declaration; customer/legal role is not inferred from this assignment. The selected organization records responsibility only and cannot create business permission. Recheck eligibility when completing/changing a declaration, creating an account or issuing a credential. A later suspension makes declarations ineligible without deleting history. Existing active credentials are still governed by the existing actual authority boundary; metadata alone is not a claim of newly enforced request scope. Full service-authentication enforcement remains an explicit dependent planning obligation.

New service.create requests require the complete declaration along with name/owner; no legacy bypass silently creates a new fully specified-looking account. Validate all fields/catalog/resource references/owner eligibility and capacity before CreateServiceUser. Commit declaration immediately after successful identity creation under the same server domain write lock with no fallible storage step afterward. No automatic network side effect is introduced. The command's existing expected revision/idempotency and replay boundary covers the complete submitted declaration. An explicit service.declare command completes or revises legacy declarations using expected revision and current authority; it never edits an in-flight unknown attempt. Declaration updates preserve original stored references/version for truthful read-back. Credential issuance is refused while the required declaration is missing/ineligible; revoke/suspend/retire and known outcome recovery remain available. Do not remove or reclassify existing uncertain issue/secret pickup records.

# Trusted catalog implementation contract for review

The next root-owned slice is `modules/servicecatalog`, a declaration catalog consumed by subsequent M04 config, commands and bounded picker handlers. It is neither a token issuer nor an effective authorization registry. Constructor input contains `audiences[]`; each has explicit `workspace`, `id`, `resource` recipient identifier and `scopes[]`. Each scope has `id`, `action`, `kind`, `fields`, three explicit selectors (`customer`, `legal_entity`, `contract`) and `period`. A selector is exactly `{any:true}` or `{id:<canonical ID>}`; omission is invalid, and an ID literally named all is distinct from a wildcard. A period is exactly `{any:true}` or canonical `from`/`until` YYYY-MM with a strictly increasing exclusive upper bound. Workspace comes from the audience record and is included in the complete Terms validated by DescribesServiceTerms. No omitted selector/period becomes unrestricted.

The recipient resource is explicitly configured as an absolute http/https URI with a host or a nonempty urn identifier. Reject userinfo, query and fragment so credentials or callback/query parameters do not become audience identifiers. It is not dereferenced and no connection-success claim is made. Audience and scope IDs use the existing128-byte ASCII identifier alphabet. Empty catalog is valid and contains no defaults; an explicit audience with no scopes is recorded with scope_count0 and grants nothing. Duplicate audience IDs within one workspace, duplicate scope IDs within one audience, malformed/unknown fields or duplicate JSON object keys are invalid. Identical IDs in distinct workspaces/audiences remain separate. Configuration file input is capped at1MiB, with technical total bounds10000 audiences and100000 scopes; these are protocol/resource bounds, not business permission defaults.

Construct and freeze the complete catalog before publishing it. Deep-copy all input/returned slices and sort copied audience/scope IDs and field sets after validation. Do not mutate caller configuration. A SHA256 fingerprint of the complete normalized explicit wire representation covers recipient, workspace, every scope action/kind/field/selector/period, independent of input list order. It is an immutable configuration fingerprint, not current permission/organization authority. Lookup and bounded audience/scope ID pages operate on immutable per-workspace/per-audience indexes. Pages accept limit1..1000 and lexical after even when absent; return a raw internal last-ID continuation only when more entries remain. Server wrappers must still authenticate, recheck resource/organization eligibility, bind signed scoped cursors and expose configured defaults; raw catalog IDs are not externally safe snapshot tokens.

Allowed next-slice files are new `modules/servicecatalog/{catalog.go,decode.go,catalog_test.go,decode_test.go}` plus responsibility splits under1500 lines if needed and this ticket's docs. No existing grant/client/principal behavior changes. Tests must demonstrate explicit selectors/periods, otherwise-valid human/install exclusions, duplicate/malformed JSON and size bounds, independent page oracles, foreign scope isolation, zero grants/defaults, deep-copy noninterference and fingerprint changes for all permission-bearing fields. Reject an absent validator. Each nonempty scope must pass the complete validator, including its fail-closed unavailable/nil-receiver behavior. An empty catalog grants no scopes and does not certify underlying authority availability. Complete business-object reference validation is intentionally deferred to command acceptance with actual producers; a catalog may describe future named resources but does not assert they currently exist or are eligible.

Independent reviewer passed the prerequisite design and actual source slice. That result does not approve this catalog contract; its separate review precedes implementation. Catalog CLI loading and server/command/UI consumers remain mandatory before full M04 integration.

Independent catalog design review returned PASS for implementation readiness only. Decoder decisions: an explicit audiences array is required in file input; top-level/field null values are rejected. Empty programmatic Config is the explicit no-catalog default and normalizes to audiences[]. Explicit audience scopes must be an array in file input; its empty form records no permissions. Recipient identifiers are capped at2048 bytes; a urn must contain a nonempty namespace identifier and namespace-specific component separated by a colon. Direct construction is subject to count and1MiB normalized representation bounds as well as decoded input. The selected party version remains explicitly insufficient as an eligibility snapshot.

# Startup configuration integration for review

The next root-owned slice wires the implemented catalog into the real CLI/server constructor before changing service commands. Add optional `--service-catalog <path>` once; omission means an explicitly constructed empty catalog. A supplied empty path/file, duplicate flag, missing/nonregular/unreadable/oversize file or invalid catalog fails startup. Read at most MaxBytes+1 through portable Go file interfaces; perform no network fetch or environment-variable substitution and never include file contents or filesystem details in error text. The local file is declarative nonsecret installation configuration, not credential input. The1MiB protocol bound applies while reading, during server parsing and to retained normalized metadata.

Pass bounded bytes via `server.Config.ServiceCatalog`. A nil byte slice means no configured catalog; a nonnil empty slice is invalid and must not silently become empty defaults. Immediately after actual gate construction, build/validate the immutable catalog using `s.gate` before client/grant registration, activation/data initialization or listener creation. Constructor failure returns the existing generic start/config error and does not write activation/history/ledger files. Keep only the immutable catalog; clear raw configuration bytes from the server's retained Config. Caller input is not mutated. Later changes to file/input bytes cannot alter a running catalog; reload/restart constructs and validates a new fingerprint and existing process cursor keys. A valid catalog is still not a connection, grant, service-account declaration or effective-scope enforcement.
